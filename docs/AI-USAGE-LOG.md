# AI Usage Log

This document provides an honest account of how Claude was used throughout the project: what was delegated to Claude, what was implemented or decided directly, where Claude provided incorrect or misleading suggestions, and how each issue was identified, corrected, and verified.

The entries are roughly chronological. This log does not claim that AI-assisted development was flawless. Instead, it intentionally documents several real and non-trivial mistakes because identifying, reviewing, and validating those mistakes is an important part of demonstrating responsible AI-assisted engineering.

## What Was Delegated to Claude

Claude was used as an engineering assistant for implementation, debugging, analysis, and review. This included:

* Scaffolding the Clean Architecture folder structure and explaining the reasoning behind each layer and its boundaries.
* Assisting with Django models, migrations, ports/adapters, use cases, agents, tools, and API views, implemented incrementally and verified step by step.
* Generating an initial version of the synthetic insurance policy corpus, which was later reviewed and corrected.
* Diagnosing issues based on actual terminal output that was provided during development, including venv/PATH problems, PostgreSQL permission errors, migration ordering, LibreOffice profile locking, and Celery signature mismatches.
* Assisting with regression tests for discovered issues, including a real multi-threaded concurrency test.
* Drafting project documentation such as the BRD, SYSTEM-DESIGN, ARCHITECTURE, ADRs, and this log.

Generated code was not treated as complete simply because it was syntactically correct or appeared reasonable. Changes were run, reviewed against the relevant requirement, and verified before being considered resolved.

## What Was Implemented or Decided Directly

The following decisions remained under the direct responsibility of the person building the project:

* Choosing the domain/twist variant.
* Choosing the technology stack: Django, Celery/Redis, and React with Redux Toolkit, React Query, React Hook Form, and React-Bootstrap.
* Deciding to defer Docker until Day 9.
* Defining the requirements and acceptance criteria that each implementation had to satisfy.
* Deciding whether an issue should continue to be debugged or should instead be documented as a known limitation.
* For example, after multiple attempts to calibrate the RRF refusal threshold, the decision was made to stop trying additional parameter values and document the embedding-anisotropy limitation instead of assuming that another threshold would solve the problem.
* Rejecting the proposed Redis-outage fallback using background threads inside the Django process after reviewing its impact on T7's resume and cancellation guarantees.
* Explicitly requesting a second, independent review of code that was already working, including the Day 6 approval gate and the FR-6 real-time implementation, rather than treating the first implementation pass as final.
* Making all final architecture decisions recorded in the ADRs.

Claude therefore provided implementation options, analysis, and review feedback, while the final engineering decisions and acceptance of changes remained under human control.

## Where the AI Misled Me, and How I Verified and Corrected It

### 1. The Synthetic Corpus Contained AI-Facing Language Instead of Realistic Policy Text

The initial corpus generated by Claude contained sections such as:

`Claim Evaluation Guidance`

and:

`policy-version-not-found condition for human review`

This language was useful for describing what a retrieval system should do, but it did not resemble authentic insurance policy wording.

**How it was caught:**

The generated content was manually reviewed, and it was clear that some sections were written for the AI/retrieval system rather than as realistic policy documents.

**Correction:**

The corpus was rewritten using a structure closer to real insurance documents, including:

* Declarations
* Insuring Agreement
* Exclusions
* Duties in the Event of Loss

The revised content was then reviewed again to verify that it looked like policy material rather than project documentation.

---

### 2. The Chunking Regex Treated a PDF Line-Wrap Fragment as a Real Heading

`NumberedHeadingChunker` initially used a regex that allowed a PDF line-wrap artifact such as:

`0026. Policy Period: from 2024-01-01...`

to be interpreted as a numbered section heading simply because it started with digits followed by a period.

**How it was caught:**

Running the evaluation harness produced a 0% hit rate.

The diagnostic output was then inspected, and the retrieved section names were clearly malformed: they contained long sentence fragments instead of actual section headings.

**Correction:**

The regex was tightened so that a valid heading must have an appropriate capitalized, short title without an internal period.

This prevented arbitrary digit-dot-text patterns from being interpreted as section headings.

---

### 3. The Refusal Threshold Was Mathematically Unreachable, Then Miscalibrated in the Opposite Direction

The initial RRF refusal threshold was `0.15`, while the theoretical maximum fused score was approximately `0.033` at `k=60`.

As a result, the system rejected almost every query, including valid ones.

After correcting `k` and adjusting the threshold, adversarial queries were rarely rejected. The actual evaluation results then showed that the fused RRF score did not provide a reliable separation between relevant and irrelevant queries.

**How it was caught:**

The evaluation harness was run after each change, and the actual per-case scores were inspected.

The overlap between adversarial and genuine queries was visible directly in the results rather than being assumed.

**Correction:**

The refusal decision was moved from the fused rank score to raw dense cosine similarity.

The decision was documented in ADR-005, and the embedding-anisotropy limitation was explicitly documented in `docs/EVALUATION.md` rather than claiming that the problem had been completely solved.

---

### 4. Stale and Duplicated Corpus Data Made Retrieval Appear Broken

After the corpus was corrected, the evaluation still returned a 0% hit rate.

The actual cause was that the local `corpus/` directory still contained the older, uncorrected files under the same filenames.

This was a stale-data problem rather than a retrieval-logic problem.

**How it was caught:**

The local files were inspected directly using commands such as:

`grep`

and:

`unzip -p`

This revealed that the files actually being used did not match the corrected corpus.

This was an important example of validating the actual repository state rather than assuming that a previously described change had been applied correctly.

---

### 5. A Non-Existent Corpus Generation Script Was Assumed to Exist

While wiring `backfill_policy_limits`, an import from `generate_corpus.py` was proposed based on the assumption that the corpus was generated by a script.

However, the actual workflow used 30 manually curated corpus files.

**How it was caught:**

The actual repository state was checked, confirming that `generate_corpus.py` did not exist and that the corpus was hand-curated.

**Correction:**

The policy limit values were moved into a small manually maintained data file instead of depending on an import from a non-existent generator script.

---

### 6. The Correlation ID Implementation Did Not Work Across Process Boundaries

The initial correlation-ID design used Python's `threading.local()` inside Django middleware.

However, this state does not cross into a separate Celery worker process.

The implementation could therefore appear correct during same-process testing while producing an empty correlation ID for real asynchronous jobs.

**How it was caught:**

The issue was identified during a review pass by checking the implementation against the actual Django/Celery process model, before relying on it in a real asynchronous execution.

**Correction:**

The correlation ID is generated in the view and explicitly passed to the Celery task as a task argument.

---

### 7. Token Counts Were Estimates Rather Than Actual Provider-Reported Usage

An initial observability implementation used:

`len(text.split())`

as a proxy for token usage because streaming responses do not provide usage information with every individual token.

**How it was caught:**

The observability requirement was reviewed and it became clear that the system needed actual provider-reported token usage rather than a word-count approximation.

**Correction:**

The streaming clients for both providers were updated to request and parse their actual final usage information:

* OpenAI uses `stream_options={"include_usage": True}`.
* Ollama uses the final `done` chunk.

The recorded token counts therefore represent provider-reported usage instead of an estimate.

---

### 8. A Race Condition in Async Step Execution Required a Real Concurrency Test

The first step-claiming implementation used `get_or_create` without sufficient locking.

This allowed two concurrent Celery task deliveries to potentially see the same step as unclaimed and execute the same agent.

**How it was caught:**

A dedicated `TransactionTestCase` was created using:

* real threads;
* a deliberately widened race window;
* real database transactions.

The test demonstrated that the race condition could actually occur.

This was important because a mock-based timing test would not have reliably exposed the problem.

**Correction:**

The implementation was changed to use:

* a database-level unique constraint on `(job, name)`;
* an insert-or-fail approach;
* `select_for_update()` where appropriate.

A lock alone cannot protect a row that does not yet exist, which is why the unique constraint and insert-or-fail behavior were necessary.

---

### 9. An Abstract-Method Error Was Initially Misdiagnosed

A `TypeError: Can't instantiate abstract class` error initially led to the suggestion that the `complete_job` method should be removed from the recorder port.

However, checking the actual call sites using:

`grep -rn "\.complete_job("`

showed that the method had no real callers and that it was not the actual cause of the immediate failure.

The error had already disappeared between messages, most likely due to save timing while editing.

**How it was caught:**

The proposed diagnosis was not accepted without evidence. The relevant grep and test commands were run again to verify the actual repository state.

This showed that the proposed fix did not match the available evidence.

---

### 10. The Redis-Outage Fallback Would Have Undermined T7's Guarantees

A background-thread fallback was proposed for situations where Redis was unavailable.

Reviewing the design showed that a background thread would die with the Django process, meaning it could not provide genuine resume behavior after a process failure.

It would also make the feature appear to work while silently bypassing T7's guarantees around:

* resume;
* cancellation;
* idempotency.

**Outcome:**

The review finding was accepted, and the fallback was removed rather than being documented as an accepted limitation.

The decision was that having no fallback was preferable to introducing a mechanism that could provide misleading behavior and bypass the core guarantees of T7.

## How Each Issue Was Verified

Each fix was treated as an evidence-based change rather than being accepted solely because the code looked correct.

After an appropriate change, the relevant verification was run, including:

* `manage.py` commands;
* the evaluation harness;
* test files;
* integration tests;
* `curl`;
* live SSE sessions.

The actual output was then inspected to confirm that the behavior matched the intended requirement.

No fix was considered complete simply because Claude stated that it had been fixed.

The verification process was:

**Implementation → Run → Observe → Review → Test → Verify**

This is the central principle behind the project's use of AI: Claude assisted with implementation, debugging, reasoning, and review, but **a change was only accepted after it was reviewed, executed, and validated against actual evidence.**
